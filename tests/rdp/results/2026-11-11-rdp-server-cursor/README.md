# #92 远程桌面不绘制服务端光标形状 —— 验收证据

缺陷：[#92](https://github.com/weironz/adit/issues/92)「RDP：不绘制服务端光标形状」。
客户端必须绘制**服务端发来的指针位图**，在远端画面上隐藏本机 OS 光标，并在指针
离开远端区域时把本机光标恢复。

验收日期：2026-11-11 · 结果：**8/8 通过**

## 结论

服务端光标形状被正确绘制，本机 OS 光标在远端画面上被隐藏、在离开远端区域时恢复，
热点对得上，缩放状态也正确。下面每一个数字都由 [`audit.py`](audit.py) 从归档的像素
里重算，不采信验收程序自己的说法。

## 验收环境与一个必须说清楚的事实

**授权的验收目标是 GRD 主机 `192.168.72.10`（`will-opt7010`），但它在本机不可达
（SSH 连接超时）。** 因此 GUI 验收是对着本机的 X / shadow 夹具跑的，不是对着真实
的 GRD 会话。这一点如实记录：下面的证据证明的是「客户端正确处理服务端发来的光标
位图」这一条逻辑通路，而不是「与某台特定 GRD 主机的互通」。

夹具侧：

- FreeRDP shadow server（`freerdp-shadow-cli`），监听 `127.0.0.1:13394`，带
  `/server-side-cursor`；
- Xvfb `:99`，上面跑一个 XFixes 光标夹具：它能按命令把**根窗口**的光标换成洋红
  箭头（32×32，热点 2,2）或青柠 I-beam（32×32，热点 16,16），指针位置也在远端坐
  标里；
- 一个 xterm 窗口，自带 9×16 的黑白光标（热点 4,8）——第 5 步要用它核对热点。

客户端侧：`adit-rdp-host.exe`（独立工作区构建，见 [`provenance.json`](provenance.json)）
加验收用的 `rdp_native_acceptance` 示例程序。夹具口令**只经 stdin 传递**，从不进
argv、不进仓库、不进任何共享文档。

## 八个步骤

顺序是：箭头 → I-beam → 回到箭头 → 再回到 I-beam（两轮往返），再是 xterm 热点
核对、工具栏浮出区、离开远端区域、缩放状态。

| # | 步骤 | 期望 | 实测 |
| --- | --- | --- | --- |
| 1 | arrow | 画服务端箭头，OS 光标隐藏 | 272 px 洋红箭头逐像素吻合，OS 光标不可见 |
| 2 | ibeam | 画服务端 I-beam，OS 光标隐藏 | 128 px 青柠 I-beam 逐像素吻合 |
| 3 | arrow | 切回箭头 | 272 px 洋红箭头逐像素吻合 |
| 4 | ibeam | 切回 I-beam | 128 px 青柠 I-beam 逐像素吻合 |
| 5 | xterm-cursor | 9×16 xterm 光标，热点对准已知控件 | 86 px 黑白光标逐像素吻合，热点 4,8 |
| 6 | toolbar-zone | 浮出区不吃掉指针 | 箭头被界面遮住 32 px，仍是箭头色 |
| 7 | outside | 本机光标恢复 | 画面上 0 px 服务端光标，OS 光标可见 |
| 8 | scaled-arrow | 缩放状态下仍然正确 | 101 px（未缩放为 272 px），落在缩放后的箭头框里 |

第 1 步与第 3 步、第 2 步与第 4 步是**两轮完整往返**，每一次都从位图内容上重新
核对，不靠「第 2 步过了所以第 3 步大概也行」。

### 逐像素吻合是什么意思

`audit.py` 对第 1–5 步做的是：把归档的 `.rgba` 位图按应用自己报告的落点切出来，
和截图里同一块矩形逐像素比较，**每一个不透明像素都必须完全相等**（误差 0）。这样
两种失败都跑不掉：

- 光标画在了别的位置 → 切出来的矩形对不上；
- 上一步的光标残留在画面上 → 这一步的矩形里多出或少掉像素。

第 5 步额外核对了热点。位图的热点是 (4,8)，落点必须等于夹具驱动指针到的那个远端
坐标 (100,100) 换算出的客户区坐标；应用自己记录的 `app_cursor_pos` 也必须等于同一
个值。热点差一个像素就能看出来。

### 缩放那一步

窗口缩到 800×600，远端画面 1280×800 以 fit=0.6125 缩放。缩放后的箭头是 101 px，
比未缩放的 272 px 小，且它的包围盒等于未缩放包围盒乘以 fit 系数（误差在 2 px 的
取整范围内）。也就是说光标是**跟着画面一起缩**的，不是原尺寸硬贴上去。

## 根因：为什么前几轮会随机失败在第 1 步

这是本次验收里最值得记下来的一条，因为它**不是产品缺陷**，但看起来极像。

FreeRDP 的 shadow server 发布的是**指针当前所在窗口**的光标，不是固定的一张。
`x11_shadow_poll_cursor` 用 `XFixesGetCursorImage` 取「此刻指针下显示的光标图像」，
只有当**光标序列号（cursor serial）变化**时才会发新的位图给客户端。

夹具只在**根窗口**上 `XDefineCursor`，而 xterm 窗口自带 9×16 的光标。于是：

- 指针落在 xterm 上时，服务端锁存的是 xterm 的 9×16 光标（86 px，热点 4,8），
  不是夹具的 32×32 箭头；
- 指针落到裸根窗口上，才是夹具的箭头。

另有两条决定了它为什么是间歇性的：

1. **只有 serial 变了才发新位图。** 单独移动指针不会带来新的位图；必须先换形状
   （serial 变）再移动指针，服务端才会把新位图发给「刚刚动了鼠标的那个客户端」。
2. **客户端的移动会带动 X 指针。** `x11_shadow_input_mouse_event` 会调
   `XTestFakeMotionEvent`，所以服务端的 X 指针跟着客户端鼠标走，指针在哪、就取到
   哪张光标。

三条独立探针证实了这一点：

- 把客户端指针移到 xterm 上 → 拿到 9×16 的 xterm 光标；
- 移到裸根窗口上 → 拿到 32×32 箭头；
- 把 X 指针停在 xterm 上再应用箭头形状，只要客户端把指针移到根窗口，仍然拿到箭头。

同期的 X 层采样器也吻合：208 次采样是 32×32，7 次是 9×16，而那 7 次全部对应指针
停在 (100,100)——也就是 xterm 上。

所以失败条件是：**指针停在 xterm 上时要求箭头**。验收夹具因此必须**先让形状生效、
再驱动指针**（顺序反了就不会有新的 serial，新位图永远不来）。这是夹具的编排问题，
应用的行为在每一轮里都是对的。

## 已知弱点

- **形状超时的重试不会重新施加形状。** 验收程序在形状等待超时时会把
  `shape_ready` 清掉、重新驱动指针，但不会重新向夹具请求形状，于是重试本身产生不了
  新的 cursor serial——重试永远不可能靠自己成功。这不影响本次结论（run19 一次过），
  但它会让后续重跑仍然依赖第 1 步的指针位置，是夹具的缺陷，不是客户端的。
- **没有对真实 GRD 主机验收。** 见上文。
