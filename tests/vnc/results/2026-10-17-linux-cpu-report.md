本轮独立补充 CPU 指标，采用固定源码 `d76f7440515b65d1123ea42de338ca2eaa87b09d` 的 Windows debug 会话探针，二进制、运行脚本 SHA-256 和容器版本见 [环境记录](2026-10-17-linux-cpu-environment.json)，180 条完整观测见 [原始数据](2026-10-17-linux-cpu.json)。它不向此前 360 次测量补填未采集的数据。

三种真实 Linux 服务端、两种画质、三种负载，各 10 次新连接，全部使用未整形回环网络和同一 800×600 合成画布。180/180 均在 15 秒首屏截止时间内完成全像素覆盖，随后完成至少 5 秒稳态窗口；失败 0 次，未完成刷新请求不超过 1。

CPU 是 Windows GetProcessTimes 取得的探针进程用户态加内核态累计时间，覆盖进程启动、握手、首屏、稳态和结束，并非单帧解码耗时，也不包含 Docker 中服务端 CPU 或原生 UI/GPU。首屏耗时不同使总进程存活时间略有差异；这里同时保留首屏和字节数据以便解释，不把这些结果当成严格隔离的编解码器排名。本机并行运行构建及其他测试，debug 构建与小样本结果不能外推生产帧率或可靠 P95。

WAN 档在六个动态负载组合中均减少本轮更新字节，同时增加客户端累计 CPU。例如 TigerVNC 拖动，无损为约 24.767 MiB / 3016 ms CPU，WAN 为约 6.753 MiB / 5219 ms CPU。静态画面不保证获益：TigerVNC 的 WAN 档本轮约 1.630 MiB，高于无损的 0.552 MiB。客户端因此保留默认无损和显式 WAN 选择，不将 JPEG 档设成所有网络的自动最优。

这些数字只证明所列服务端、负载和配置下的表现。字节计数为已完成 framebuffer 更新，不包含 TCP/TLS 开销。交互负载由固定脚本产生，未测完整鼠标到画面延迟。弱网首屏与流量另见 [360 次主矩阵报告](2026-10-17-linux-steady-report.md)；Windows 服务模式、锁屏、UAC、IME 与 DPI 仍须分别验收。
